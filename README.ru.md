# @vetojs

**[English](README.md) · [Русский](README.ru.md)**

**Type-safe авторизация без классов, магии и скрытого состояния.**

Политика — это чистая функция. Она принимает пользователя (или любой другой контекст) и возвращает массив правил в виде обычного JSON. Этот массив без проблем передаётся с сервера на клиент. Он же отвечает за строгую проверку прав с полным выводом типов и элегантно превращается в безопасный `WHERE` для вашей базы данных.

- **Правила — плоские данные и пересекают любую границу.** Идеально для React Server Components — и ровно так же для `load` в SvelteKit, пейлоада Nuxt или вызова инструмента агентом.
- **Автоматически превращается в SQL.** Политика, отвечающая за `can()`, транслируется в условие `WHERE`. База данных вернёт ровно те строки, которые пользователю разрешено видеть.
- **Запись проверяется по полям.** [`validatePayload`](docs/mutations.ru.md) отвечает, какие поля и какие значения этому пользователю можно писать, и называет каждое нарушение — ровно ту фразу, по которой клиент API или модель исправит свой запрос.
- **Правила могут жить в базе.** [`parseRules`](docs/parse.ru.md) проверяет недоверенный JSON правил на границе, а незнакомое коду правило отбрасывается — поэтому база, ушедшая вперёд деплоя, способна только сузить доступ.
- **Не ломается на плохих данных.** Значение неверного типа или пропавшее поле могут сузить доступ, но никогда его не расширят.
- **5.4 kB в gzip.** За этот объём вы получаете валидацию правил с сервера, сборку ability и проверку строки. Если правилам уже можно доверять, размер падает до 3.9 kB. Проверка внутри серверного компонента обойдётся всего в 98 байт.
- **0 зависимостей.** Проверять на безопасность нужно только одно — код, который непосредственно управляет доступом.
- **Работает везде, где есть JavaScript.** Никаких привязок к встроенным модулям Node, файловой системе или динамическому выполнению кода. Библиотека нативно поддерживает Workers, Deno, Bun и любые edge-рантаймы.

```sh
npm install @vetojs/core
```

## Как это работает: три простых шага

```ts
import { defineAbilities, shape, createRules, buildAbility } from "@vetojs/core";

// 1. Опишите схему ресурсов один раз.
const ac = defineAbilities({
	resources: {
		post: {
			schema: shape<{ id: string; authorId: string; status: "draft" | "published" }>(),
			actions: ["read", "update", "publish"],
			relations: { author: { resource: "user", kind: "one" } },
		},
		user: { schema: shape<{ id: string; role: string }>(), actions: ["read"] },
	},
});

// 2. Политика — функция, которая возвращает массив правил.
const { allow, deny } = createRules(ac);

const policyFor = (user: { id: string }) => [
	allow("read", "post", { where: { status: "published" } }),
	allow(["update", "publish"], "post", { where: { authorId: user.id } }),
];

// 3. Передайте правила в движок — и проверяйте доступ.
const ability = buildAbility(ac, policyFor(currentUser));

ability.can("update", "post", post);  // ✓ типизировано по вашей схеме
ability.can("delete", "post");        // ✗ ошибка компиляции — у "post" нет "delete"
```

Опечатки больше не доедут до продакшена: если действие, ресурс, поле или оператор не совпадают с вашими типами, код просто не скомпилируется.

## Почему не CASL?

CASL — это отличный инструмент и признанный лидер. Но он создавался до эпохи React Server Components, и в его основе лежат экземпляры классов, из-за чего наши архитектурные пути расходятся. Сравнение актуально для `@casl/ability@7.0.1`.

| | CASL | @vetojs |
|---|---|---|
| **Сервер → клиент** | ability — это экземпляр `PureAbility`, который RSC не пропускает: *«Only plain objects… Classes or null prototypes are not supported»* ([#999](https://github.com/stalniy/casl/issues/999)). | `ability.rules` — это обычный JSON. Клиент легко пересобирает ability из него. |
| **Пометка объекта** | `subject("Post", post)` **мутирует** сам `post`, добавляя неперечислимую метку. Из-за этого `JSON.stringify` её теряет, и тип пропадает молча. | `can("update", "post", post)` принимает имя ресурса как простой аргумент. Никаких обёрток и мутаций данных. |
| **Типизация** | Сузить действия по ресурсу можно, но объединения часто приходится писать руками (например: `MongoAbility<["create" \| "manage", "campaign"] \| ["create" \| "delete", "user"]>`). | Все действия, ресурсы и формы автоматически выводятся из одного объявления `defineAbilities`. |
| **Запросы к базе** | Метод `accessibleBy` требует отдельного адаптера под каждую ORM. Поддержка SQL [открыта с 2017 года](https://github.com/stalniy/casl/issues/8), а с выходом новых мажорных версий ORM придётся ждать релиз адаптера. | `ability.where()` отдаёт стандартное дерево условий, которое легко обойти самому. Пакет `@vetojs/drizzle` сразу превращает его в SQL с гарантией: запрос вернёт ровно то, что разрешает `can()`. |
| **Зависимости** | 4 | 0 |
| **Размер бандла** | ~7.0 kB за весь пакет (6.3 kB gzip для сборки и проверки). В бандл уезжает лишний код (например, `$elemMatch`), даже если политика его не использует. | 5.4 kB gzip на ту же проверку с валидацией пришедших правил. 3.9 kB без валидации. Весь пакет целиком — 6.6 kB. |
| **Плохие данные** | Оператор `$gt: 50` может пропустить строку `views: "100"`, а `deny` по `secret: true` не сработает на `secret: "true"`. | Значение, не подходящее под условие, строго даёт «неизвестно». `allow` не сработает, а `deny` отработает надёжно. |

Переходите с CASL? [Переход с CASL](docs/migrate-from-casl.ru.md) подробно сопоставляет API, называет операторы без аналогов и разбирает два отличия в поведении, которые могут повлиять на логику вашей политики.

## Сколько стоит проверка

Условие превращается в функцию при первом же вычислении, и ability её сохраняет. Поэтому первая проверка ресурса платит за компиляцию, а каждая следующая просто вызывает функцию — ровно та форма, которая нужна первому рендеру и SSR, когда одна политика отвечает про страницу, полную строк.

Замер на политике, какую пишет настоящее приложение, — пять правил, среди них `allow(["update", "publish"], "post", { where: { authorId: user.id, status: { ne: "draft" } } })`, — по сотне строк, Node 24:

| | |
|---|---|
| собрать ability на запрос | 0.11 мкс |
| проверить одну строку | 0.12 мкс |
| закрыть сотню строк | 6.7 мкс |
| собрать и закрыть сотню строк | 8.4 мкс |
| `ability.where()` для базы | 0.3 мкс |
| разобрать пришедший текст правил, проверить и собрать | 5.0 мкс |

Запомнить стоит две. **Восемь микросекунд** — это всё, что запрос платит за сборку политики и решение по сотне строк; остальной запрос этого не заметит. А `ability.where()` за **0.3 мкс** — это альтернатива всему перечисленному: отдайте условие базе и не гейтите в JavaScript ничего.

Правила, приехавшие текстом, стоят на разбор и проверку около трёх четвертей гейтинга сотни строк: [`parseRules`](docs/parse.ru.md) — это граница доверия, и она же единственное место, которое стоит кешировать, если политика приходит на каждый запрос, а не на сессию.

Против `@casl/ability@7.0.1` на тех же правилах и тех же строках, оба движка собранными пакетами, медиана десяти прогонов — каждая цифра рядом с моментом, когда за неё платят:

- **Сборка политики: быстрее в ~45 раз.** Это цена одного запроса. Серверный компонент собирает ability на каждый рендер и каждую навигацию; CASL заранее строит индекс правил и тратит на это около 8 мкс, мы снимаем копию массива и тратим 0.2. На странице из пары десятков закрытых правами компонентов это разница между заметным прогревом и его отсутствием.
- **Отказ по строке: быстрее в 2.6 раза.** Отрицательный ответ — самый частый: спрятанная кнопка, строка, не попавшая в список, — и список оплачивает его сотню раз подряд.
- **Проход по загруженной связи: быстрее в 1.4 раза.** Правила по членству — `post.blog.workspace` — это то, как пишутся мультиарендные политики, то есть путь, по которому идёт настоящая.
- **Политика из 222 правил, где разрешает раннее правило: быстрее в 8–10 раз.** Так выглядит политика, сгенерированная на каждого тенанта вместо роли.
- **Те же 222 правила, когда разрешающее правило лежит последним: быстрее в 2.3 раза у них.** `deny` побеждает, где бы он ни лежал, поэтому «да» обязано увидеть каждый запрет, а CASL останавливается на первом совпавшем правиле — приоритет у него позиционный. Это цена того, что правила — множество, а не список, и [форма политики, которую и так не стоит писать](docs/create-rules.ru.md#одно-правило-на-роль-а-не-на-тенант): сгруппированные по ролям, эти 222 правила сжимаются до дюжины — то есть во вторую строку выше.

## Где решает та же политика

Одна функция политики — и проверка в каждом месте, где решение действительно принимается. Ни одному из них не нужен отдельный пакет.

- **[Server actions и RSC](docs/guard.ru.md)** — `createGuard` находит пользователя, загружает строку, проверяет payload и только потом запускает обработчик.
- **[HTTP-обработчики](docs/http.ru.md)** — Express, Fastify, Hono. Обработчик — это функция, а гвард оборачивает функции; различается только то, где на запросе лежит пользователь и как отказ превращается в статус.
- **[Вызовы инструментов агентом](docs/agents.ru.md)** — аргументы там догадка модели, а не заполненная человеком форма. Та же политика отвечает на вопрос «можно ли человеку, от имени которого действует агент, сделать это с *этой* строкой», а отказ называет поле — именно поэтому модель исправляется, а не повторяет тот же вызов.
- **[Server rendering за пределами RSC](docs/ssr.ru.md)** — `load` в SvelteKit, пейлоад Nuxt, пропсы островов Astro, лоадеры React Router. Правила — это JSON, поэтому они едут тем каналом, который у фреймворка уже есть.
- **[База данных](docs/where.ru.md)** — те же правила в виде `WHERE`, одинаково на чтении и на записи, с гарантией: запрос вернёт ровно то, что разрешает `can()`.
- **[Рядом с Postgres RLS](docs/rls.ru.md)** — как эти двое сочетаются и три способа, которыми row-level security незаметно не защищает ничего.

## Единый источник правды от БД до клиента

На уровне базы данных мы запрашиваем только то, что позволено пользователю: правила автоматически конвертируются в условие `WHERE`.

```ts
const rows = await db.select().from(posts)
	.where(schema.filter(ability, "read", "post"));
```

Тот же предикат уместен и на записи. Скрытая политикой строка не совпадёт — запрос не тронет ничего, и между чтением и проверкой не остаётся окна:

```ts
const [updated] = await db.update(posts).set(data)
	.where(schema.filter(ability, "update", "post", eq(posts.id, "p1")))
	.returning();
```

На сервере (в серверных компонентах) мы проверяем доступ к конкретной строке и безопасно передаём правила клиенту в виде плоских данных:

```tsx
const ability = buildAbility(ac, policyFor(user));
if (!ability.can("read", "post", post)) notFound();

return (
	<AbilityProvider rules={ability.rules}>
		<Toolbar post={post} />
	</AbilityProvider>
);
```

На клиенте те же самые правила управляют интерфейсом, скрывая или показывая элементы управления:

```tsx
"use client";

<Can I="update" a="post" this={post} fallback={<DisabledButton />}>
	<EditButton />
</Can>
```

И сервер, и клиент опираются на один и тот же массив JSON-правил, поэтому рассинхронизация логики доступа просто невозможна.
