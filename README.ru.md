# ⚡ @vetojs

> Авторизация для TypeScript-приложений и ИИ-агентов, которые в них работают. Право пишется один раз — ему подчиняются обработчик, SQL-запрос, интерфейс и каждый вызов инструмента.

[![NPM version](https://img.shields.io/npm/v/%40vetojs%2Fcore?label=%40vetojs%2Fcore)](https://www.npmjs.com/package/@vetojs/core)
[![License](https://img.shields.io/npm/l/%40vetojs%2Fcore)](LICENSE)

**[English](README.md) · [Русский](README.ru.md)**

Доступ обычно описан четырежды: `if` в обработчике, `WHERE` в запросе, ручная чистка полей перед `UPDATE` — а когда в приложении появляется агент, ещё и строчка в системном промпте с просьбой не выходить за данные пользователя. Четыре копии одного правила разъезжаются по очереди, а четвёртая и вовсе не правило: о чём попросил один промпт, от того другой может модель отговорить.

Здесь право пишется один раз. Политика — это функция, которая принимает пользователя и возвращает массив правил, и этот один массив:

- **отвечает на `can()`** — можно ли этому пользователю это действие с этой строкой;
- **становится `WHERE` запроса** — список вернёт ровно те строки, что разрешает `can()`, а тест сверяет оба пути на одних и тех же строках в Postgres, `NULL` включительно;
- **проверяет запись по полям** — и отказ называет поле, которое нужно поправить;
- **решает, что может тронуть вызов инструмента** — от имени человека, за которого действует агент;
- **уезжает на клиент как есть** — и решает, что покажет интерфейс.

## Когда вызывает ИИ-агент

Вызов инструмента — это эндпоинт, на другой стороне которого языковая модель. Его аргументы не заполнил человек в форме, их угадали — и модель попросит чужую строку, стоит схеме сказать `id: string`.

Поэтому вопрос не «можно ли этому агенту редактировать посты», а «можно ли человеку, от имени которого он действует, опубликовать *этот* пост» — тот самый, который уже задаёт интерфейс, и отвечает на него та же политика. `withPermission`, который охраняет server action, оборачивает и инструмент:

```ts
type PublishArgs = { id: string; status: "draft" | "published" };

const publish = withPermission(
	{
		action: "publish",
		resource: "post",
		load: (args: PublishArgs) => loadPost(args.id),
		payload: (args: PublishArgs) => ({ status: args.status }),
	},
	async (ctx) => `published ${ctx.row.id}`,
);
```

Гвард загружает строку, которую назвала модель, и сверяет её с политикой человека до того, как запустится обработчик. id из чужого воркспейса получает отказ сразу. Значение, которое человеку ставить нельзя, получает отказ с названием поля — `violations: [{ field: "status", reason: "value not permitted" }]`, — и когда это попадает в ответ инструмента, модель исправляет аргумент, а не повторяет тот же вызов.

- **Чтение идёт через ту же политику.** Инструмент поиска фильтрует в SQL через `schema.filter` и отдаёт то, что видно человеку, а не серверу. Именно на выборке агент с лишними правами течёт тихо: ничего не падает, модель просто видит больше.
- **Инструмент без таблицы тоже проверяется.** Почта, файлы, вебхуки, платежи: строку собирают из аргументов, которые выбрала модель, — домен получателя, сумма, каталог для записи, — и политика судит её, как любую другую.
- **Агенту можно дать меньше, чем его пользователю.** Объявите ключ окружения и поставьте на него запрет — `deny("delete", "invoice", { when: { viaAgent: true } })`, — и та же политика не даст агенту удалить то, что человеку удалять можно.
- **MCP и Anthropic SDK обходятся без пакета-обёртки.** Пользователь берётся из `extra.authInfo` в обработчике MCP или из окружающего кода, когда инструмент создаётся под конкретный разговор.

veto ограничивает полномочия, но не распознаёт манипуляцию. Модель, которую уговорили, всё равно получит не больше, чем мог бы сделать человек, за которого она действует, — и эта граница задана данными, которые проверяются тестом, а не фразой в промпте. Интеграции целиком — на странице [«Как охранять то, что делает агент»](docs/agents.ru.md).

А когда код пишет ассистент, весь API собран на одной странице — [docs/for-agents.ru.md](docs/for-agents.ru.md) и [llms.txt](llms.txt): дайте ссылку Claude, Cursor или Copilot, и подсказки будут по делу.

## Quick Start

### 1. Установка

```sh
npm install @vetojs/core
# или
pnpm add @vetojs/core
```

Только ESM, Node.js 20 и новее.

### 2. Объявите ресурсы и политику

```ts
import { defineAbilities, shape, createRules, buildAbility } from "@vetojs/core";
import type { ActionFor, ResourceName } from "@vetojs/core";

const ac = defineAbilities({
	resources: {
		post: {
			schema: shape<{ id: string; authorId: string; status: "draft" | "published" }>(),
			actions: ["read", "update", "publish"],
			relations: { author: { resource: "user", kind: "one" } },
		},
		user: { schema: shape<{ id: string; role: string }>(), actions: ["read"] },
	},
});

const { allow } = createRules(ac);

const policyFor = (user: { id: string }) => [
	allow("read", "post", { where: { status: "published" } }),
	allow(["update", "publish"], "post", { where: { authorId: user.id } }),
];

const ability = buildAbility(ac, policyFor({ id: "u_1" }));
```

### 3. Спрашивайте — типы уже выведены

`defineAbilities` — единственное место, где вы что-то объявляете руками. Список ресурсов и список действий для каждого из них редактор выводит сам:

```ts
type Resources = ResourceName<typeof ac>;
//   ^? "post" | "user"

type PostActions = ActionFor<typeof ac, "post">;
//   ^? "read" | "update" | "publish" | "manage"

ability.can("publish", "post", post);
//           ^| автодополнение подставит эти три и никаких других
```

`manage` добавляется к каждому ресурсу для правил — это подстановочное действие, покрывающее все остальные. Вопрос называет действие, о котором спрашивает, поэтому `can` предлагает только объявленные, без `manage`.

Оттуда же берутся и ошибки:

```ts
ability.can("archive", "post");
//          ^^^^^^^^^ ✗ Argument of type '"archive"' is not assignable to parameter of type 'ActionFor<…, "post">'

allow("read", "post", { where: { statuz: "published" } });
//                               ^^^^^^ ✗ Object literal may only specify known properties, but 'statuz' does not exist… Did you mean to write 'status'?

allow("read", "post", { where: { status: "archived" } });
//                                       ^^^^^^^^^^ ✗ Type '"archived"' is not assignable to type '"draft" | "published" | ScalarOperators<…>'
```

Действие, ресурс, поле или значение, разошедшиеся с объявлением, — это ошибка компиляции, а не отказ в проде.

## Одни и те же правила во всех слоях

- **[Server actions и HTTP-обработчики](docs/guard.ru.md)** — `createGuard` находит пользователя, загружает строку, проверяет payload и только потом запускает обработчик. Express, Fastify и Hono [отдельного пакета не требуют](docs/http.ru.md).
- **[Серверный рендеринг](docs/ssr.ru.md)** — правила — это JSON, поэтому они едут в пропсах RSC, `load` в SvelteKit, пейлоаде Nuxt или пропсах островов Astro.
- **[Postgres RLS](docs/rls.ru.md)** — как они сочетаются и три способа, которыми row-level security молча не защищает ничего.

### От базы до кнопки — один массив правил

Дальше — один и тот же пост проходит четыре слоя. Ни на одном из них права не переписывают заново.

Запрос к базе возвращает только разрешённые строки: `schema.filter` подставляет условие правил в `WHERE`.

```ts
const rows = await db.select().from(posts)
	.where(schema.filter(ability, "read", "post"));
```

Тот же предикат работает на записи: скрытая политикой строка не совпадёт, запрос не тронет ничего, и между чтением и проверкой не остаётся окна:

```ts
const [updated] = await db.update(posts).set(data)
	.where(schema.filter(ability, "update", "post", eq(posts.id, "p1")))
	.returning();
```

Серверный компонент проверяет доступ к конкретной строке и отдаёт правила клиенту плоскими данными:

```tsx
const ability = buildAbility(ac, policyFor(user));
if (!ability.can("read", "post", post)) notFound();

return (
	<AbilityProvider rules={ability.rules}>
		<Toolbar post={post} />
	</AbilityProvider>
);
```

На клиенте те же правила управляют интерфейсом:

```tsx
"use client";

<Can I="update" a="post" this={post} fallback={<DisabledButton />}>
	<EditButton />
</Can>
```

Кнопка, запрос и строка в базе опираются на один массив JSON-правил, поэтому разъехаться им негде.

## Как это устроено

Вопросы, которые появляются, когда сама идея уже подошла: что будет на кривых данных, где могут жить правила, сколько библиотека весит и что тянет за собой.

- **Кривые данные не открывают доступ.** Поле не того типа или пропавший ключ дают вердикт «неизвестно». Разрешение на таком вердикте не срабатывает, запрет — срабатывает: доступ может только сузиться, но не расшириться.
- **Правила можно хранить в базе.** [`parseRules`](docs/parse.ru.md) проверяет форму пришедшего JSON и сообщает о каждой ошибке с путём; `buildAbility` не примет правило, которое эту проверку пропустило.
- **Условие может сравнить два поля строки** — `{ spent: { lte: { ref: "limit" } } }` — одинаково в памяти и в SQL.
- **Правило может зависеть от запроса.** Объявите `env` — час, IP, прошла ли сессия MFA, — и правило прочитает его в `when`, а [`withEnv`](docs/ability.ru.md#withenv--окружение-запроса) подставит значения одного запроса. Ключ, которого в запросе нет, запрет не снимает.
- **Правила — обычный JSON, а не экземпляры классов.** Их кладут в пропсы серверного компонента, в `load` SvelteKit или в пейлоад Nuxt — и на другой стороне они работают как есть.
- **Скрытого состояния нет.** Кроме двух классов ошибок, классов в пакете нет. `buildAbility` ничего не мутирует и ничего не кеширует между запросами.
- **Типы выводятся сами.** Одно объявление `defineAbilities` — дальше действия, ресурсы, поля и операторы подставляет редактор. Ручных дженериков нет, `any` нет.
- **5.4 kB в gzip.** Столько весит на клиенте полный путь — проверить пришедшие правила, собрать ability, проверить строку. Если правилам можно доверять, размер падает до 3.7 kB, а проверка внутри серверного компонента обойдётся всего в 98 байт.
- **0 зависимостей.** Обновлять и проверять на уязвимости придётся один пакет, а не дерево.
- **Работает везде, где есть JavaScript.** Node, браузер, Cloudflare Workers, Vercel Edge, Deno, Bun — один и тот же бандл, без платформенных веток.

### Сколько стоит проверка

Авторизация срабатывает не один раз за запрос: на каждый рендер, на каждую строку списка, на каждую кнопку. Поэтому считать надо не одну проверку, а её цену в цикле.

Условие компилируется в функцию при первом вычислении, и ability её сохраняет. Первая проверка ресурса платит за компиляцию, каждая следующая вызывает готовую функцию — та форма, которая нужна первому рендеру и SSR, где одна политика отвечает про страницу, полную строк.

Замер на политике из пяти правил, среди которых `allow(["update", "publish"], "post", { where: { authorId: user.id, status: { ne: "draft" } } })`, по сотне строк, Node 24:

| | |
|---|---|
| собрать ability на запрос | 0.19 мкс |
| проверить одну строку | 0.17 мкс |
| закрыть сотню строк | 9.3 мкс |
| собрать и закрыть сотню строк | 13 мкс |
| `ability.where()` для базы | 0.4 мкс |
| разобрать пришедший текст правил, проверить и собрать | 6.6 мкс |

`ability.where()` убирает гейтинг там, где строки приходят запросом: база отдаёт уже разрешённые, и проверять в JavaScript нечего. Что уже лежит в памяти — вложенный список комментариев, ответ стороннего API — по-прежнему должен проходить через `can()`.

[`parseRules`](docs/parse.ru.md) — граница доверия и единственное место, которое стоит кешировать, когда политика приходит на каждый запрос, а не на сессию.

## Сравнение с CASL

CASL решает ту же задачу на другой архитектуре. Если вы выбираете между ними или переезжаете, ниже — места, где разница видна прямо в коде; каждая строка проверена запуском на `@casl/ability@7.0.1`.

| Задача | CASL | @vetojs |
|---|---|---|
| **Отдать права на клиент** | Ability — экземпляр класса, он не сериализуется. На клиент уезжает `ability.rules`, и там ability надо собрать заново — фабрикой `createMongoAbility(rules)`, потому что она сама подставляет матчер условий. Голый конструктор `new Ability(rules)` без такого матчера просто бросает исключение. | Пересылать нечего: `ability.rules` **и есть** политика. На другой стороне `buildAbility(ac, rules)` — функция над тем же массивом. |
| **Проверить конкретную строку** | Строку сперва нужно пометить. `subject("Post", post)` **мутирует** объект, дописывая неперечислимое поле `__caslSubjectType__`; `JSON.stringify` его не сохраняет, поэтому строка, приехавшая с сервера, получает отказ. | Имя ресурса — аргумент: `can("update", "post", post)`. Объект остаётся нетронутым. |
| **Объявить действия и ресурсы** | Пары «действие — субъект» перечисляются в типе руками: `MongoAbility<["create" \| "manage", "campaign"] \| ["create" \| "delete", "user"]>`. Список растёт вместе с политикой. | Одно объявление `defineAbilities`. Действия, ресурсы и форма каждой строки выводятся из него. |
| **Отфильтровать выборку в базе** | `accessibleBy` работает только через адаптер под конкретную ORM. Для Prisma и Mongoose они есть, для [SQL и Sequelize запрос открыт с 2017 года](https://github.com/stalniy/casl/issues/8). | `ability.where()` возвращает дерево условий — его можно скомпилировать самому. `@vetojs/drizzle` компилирует в SQL, а тест сверяет результат построчно: запрос вернёт ровно то, что разрешает `can()`. |
| **Значение не того типа** | Сравнение приводит типы: `{ views: { $gt: 50 } }` пропустит `views: "100"`, а `deny` по `secret: true` не сработает на `secret: "true"` — запрет молча не применится. | Вердикт — *неизвестно*: `allow` не разрешает, `deny` срабатывает. Испорченное значение может только сузить доступ. |
| **Взять в проект** | 1 прямая зависимость, 4 в дереве | 0 зависимостей |

Размер имеет значение там, где правила едут в браузер. [Тест](packages/core/tests/readme-size.test.ts) собирает обе библиотеки одинаково — esbuild, минификация, затем gzip:

| | CASL | @vetojs |
|---|---|---|
| собрать ability из доверенных правил и проверить строку | 6.3 kB gzip | **3.7 kB gzip** |
| то же, но сперва проверив пришедшие правила | такого шага нет | 5.4 kB gzip |
| весь пакет целиком | 6.9 kB gzip | 7.0 kB gzip |
| закрыть серверный компонент | — | 98 байт |

Скорость сравнивалась на тех же правилах и тех же строках, что и в разделе [сколько стоит проверка](#сколько-стоит-проверка), медиана десяти прогонов. Рядом с каждой цифрой — момент, когда за неё платят:

- **Сборка политики — в ~38 раз быстрее.** Серверный компонент собирает ability заново на каждый рендер и каждую навигацию, так что это цена одного запроса. CASL заранее строит индекс правил и тратит на 222 правила около 11 мкс, `buildAbility` не строит ничего — он замыкается над массивом и тратит 0.3.
- **Отказ — в 2.6 раза быстрее.** «Нельзя» — самый частый ответ: скрытая кнопка, строка, не попавшая в список. В списке он повторяется сотню раз подряд.
- **Проверка через связь — в 1.4 раза быстрее.** Мультиарендные политики почти всегда проверяют членство по цепочке вроде `post.blog.workspace`, так что это не редкий случай, а основной путь.
- **222 правила, разрешение находится рано — в 7.7–10 раз быстрее.** Столько правил набирается, когда их генерируют на каждого тенанта, а не на роль. Когда не совпадает ничего, выигрыш падает до 1.7 раза.
- **Те же 222 правила, когда разрешение лежит последним — в 2.3 раза быстрее у CASL.** У CASL приоритет позиционный: он останавливается на первом совпавшем правиле. Здесь `deny` побеждает, где бы он ни лежал, поэтому ответ «да» обязан досмотреть все запреты. Проигрыш виден только на политике, [которую и так не стоит писать](docs/create-rules.ru.md#одно-правило-на-роль-а-не-на-тенант): сгруппируйте эти 222 правила по ролям — останется дюжина, и вы вернётесь к предыдущему пункту.

[Переход с CASL](docs/migrate-from-casl.ru.md) сопоставляет API, называет операторы без аналогов и разбирает два отличия в поведении, способные изменить решение вашей политики.

## Roadmap

- `@vetojs/prisma` и `@vetojs/kysely` — те же условия ещё в две ORM.
- Диалекты помимо Postgres в `@vetojs/drizzle`.
- `@vetojs/next` больше не развивается: гвард переехал в `@vetojs/core/guard` и работает с любым фреймворком.

Не хватает своего пункта? [Заведите issue](https://github.com/ivan-yuldashev/vetojs/issues/new) — какой ORM, какой фреймворк, какой сценарий. Порядок в списке определяется тем, что просят.

Порядок работы, требования к коммитам и changeset описаны в [CONTRIBUTING.md](CONTRIBUTING.md), правила поведения — в [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md), сообщения об уязвимостях — в [SECURITY.md](SECURITY.md).

```sh
pnpm install
pnpm test           # vitest
pnpm test:coverage
pnpm typecheck      # tsc по всему workspace
pnpm check          # biome
pnpm knip           # поиск неиспользуемых экспортов
```
