# Как принимается решение

**[English](rule-evaluation.md) · [Русский](rule-evaluation.ru.md)**

Движок получает список правил и вопрос — *можно ли этому пользователю `update` вот этот `post`?* — и отвечает «да» или «нет». Весь алгоритм умещается в две строки:

> **Явный `deny` всегда сильнее. Что не разрешено явно — запрещено.**

Дальше на этой странице — что именно эти две строки означают.

## Какие правила участвуют

Правило вступает в дело, если выполнены оба условия:

1. **совпал ресурс** — `rule.resource === "post"`;
2. **совпало действие** — правило называет его прямо, перечисляет в списке или указывает `"manage"` (это сразу все действия над ресурсом).

У подошедшего правила вычисляется `where` по строке. Правило без `where` действует на все строки.

## Решение

1. **Сработал хоть один `deny` → запрещено.** Обжалованию не подлежит, сколько бы разрешений ни нашлось.
2. Иначе **сработал хоть один `allow` → разрешено.**
3. Иначе **запрещено** — это состояние по умолчанию.

```ts
const rules = [
	allow("update", "post"),
	deny("update", "post", { where: { status: "published" } }),
];

ability.can("update", "post", { ...post, status: "draft" });     // true
ability.can("update", "post", { ...post, status: "published" }); // false — запрет сильнее
```

## Когда данные не сходятся с правилом

`where` отвечает «да», «нет» или **«неизвестно»**. Последнее — когда строка и условие несовместимы: поле не того типа, испорченная связь, сломанный список (см. [операторы](./operators.ru.md)). «Неизвестно» обрабатывается несимметрично, и так задумано:

| вердикт | правило `allow` | правило `deny` |
|---|---|---|
| да | разрешает | запрещает |
| неизвестно | не даёт ничего | **запрещает** |
| нет | не даёт ничего | не применяется |

Перечитайте среднюю строку: на «неизвестно» запрет срабатывает. Иначе хватило бы прислать значение не того типа, чтобы проскользнуть мимо запрета: `deny` решил бы, что эта строка ему не подходит, и отступил. Оба столбца работают в пользу запрета, поэтому плохие данные способны только сузить доступ.

`deny` отступает лишь тогда, когда его условие для этой строки **заведомо ложно**.

## Почему так устроено

- **Приоритет запрета и запрет по умолчанию зафиксированы — настроить их нельзя.** Именно поэтому те же правила механически превращаются в SQL `WHERE` вида `OR(разрешения) AND NOT OR(запреты)`: без решателя, без нормализации, и база возвращает ровно те строки, которые разрешил бы `can()`. Сделайте приоритет настраиваемым — и эта гарантия исчезнет.
- **`"manage"` покрывает любое действие** — и как отдельное значение, и внутри списка, одинаково для разрешений и запретов. Вопрос его не называет: такой вопрос не выбирает ни одного правила и получает отказ.
- **Этому уровню нужна строка.** Он отвечает, можно ли действовать над *этой* строкой. Вопрос «показывать ли кнопку вообще», когда строки ещё нет, решает `can(action, resource)` без строки — см. [ability](./ability.ru.md).
- **Незагруженная связь роняет исключение, а не даёт тихий отказ.** Если `where` заглядывает в связь, которую вы не загрузили, поднимается `RelationNotLoadedError`: ошибка в запросе становится видимой, а не подменяет ответ.
- **После сработавшего `allow` остальные разрешения пропускаются.** Изменить исход способны только запреты — их условия и остаётся вычислить.
