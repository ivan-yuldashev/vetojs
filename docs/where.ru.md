# Фильтрация в базе — `where()`

**[English](where.md) · [Русский](where.ru.md)**

Проверять строки по одной получится только тогда, когда они уже загружены. Для списка нужно обратное: пусть база сразу вернёт лишь то, что пользователю можно видеть. Условие для такого запроса и выдаёт `ability.where(action, resource)`.

```ts
const filter = ability.where("read", "post");
```

На выходе — обычное дерево условий, той же формы, что и в правилах. Адаптер базы превращает его в настоящий `WHERE`; с [адаптером Drizzle](./drizzle.ru.md) это один вызов:

```ts
const rows = await db.select().from(posts)
	.where(schema.filter(ability, "read", "post"));
```

## Гарантия

Фильтр отбирает **ровно** те строки, которые разрешил бы `can()`, — не больше, чтобы не перепроверять результат в коде, и не меньше, чтобы не прятать законные строки:

```
can(action, resource, row)   ⟺   строка подходит под where(action, resource)
```

В этом равенстве весь смысл режима, и оно закреплено тестом: оба пути прогоняются по одному набору строк — включая грязные, с `null`, пропущенными полями и значениями не того типа, — и результаты обязаны совпасть. Адаптер Drizzle прогоняет тот же набор на настоящем Postgres.

## Как правила складываются в одно условие

```
( сработало какое-нибудь разрешение )  AND NOT  ( сработал какой-нибудь запрет )
```

И это весь алгоритм: ни решателя, ни нормализации. Так можно, потому что [правила принятия решения зафиксированы](./rule-evaluation.ru.md): запрет всегда сильнее, а всё остальное по умолчанию запрещено.

Часть случаев сворачивается:

| Правила | Фильтр |
|---|---|
| ни одно разрешение не подходит | не отбирает ничего |
| безусловное разрешение (например, `manage`) | просто `NOT(запреты)` |
| безусловный запрет | не отбирает ничего |
| разрешения плюс условные запреты | `разрешения AND NOT запреты` |

Отдельные узлы для «ничего» и «всего» не понадобились: пустой `or` удовлетворить невозможно, а пустой `and` невозможно нарушить.

## Строка видна только при определённом «да»

Фильтр — это условие, а не готовый ответ «да/нет», и на несовместимых данных оно может сказать «неизвестно». В выборку строка попадает **только при определённом «да»**; «неизвестно» её отсекает.

Точно так же ведёт себя и сам SQL: `WHERE` отбрасывает строки, где предикат `FALSE` *или* `UNKNOWN`. Благодаря этому два режима не просто похожи, а совпадают.

**Если пишете свой адаптер**, соблюдайте этот договор: несовпадение типов должно давать `UNKNOWN`, а не приводиться к общему типу. Стоит Postgres сравнить `'5000' > 1000` как числа — и он пропустит строку, которую проверка в памяти запрещает, а гарантия выше тихо перестанет выполняться.

## Почему так устроено

- **`where()` не требует строки** — он *и есть* условие запроса. По конкретной строке отвечает `can()`. Это два честных режима, и сходятся они по построению.
- **«Истина» и «ложь» выражены уже существующими пустыми узлами**, поэтому обрабатывать их умеют все, и новый вид узла не понадобился.
