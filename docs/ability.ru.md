# Как проверять доступ — `buildAbility`

**[English](ability.md) · [Русский](ability.ru.md)**

`buildAbility(ac, rules)` превращает массив правил в объект, к которому вы обращаетесь. Каждый метод привязан к вашей схеме ресурсов, поэтому действие, ресурс и форма строки проверяются прямо по ходу написания кода.

```ts
const ability = buildAbility(ac, policyFor(user));

ability.can("update", "post", post);        // может ли этот пользователь изменить эту строку?
ability.can("update", "post");              // может ли он вообще менять посты?
ability.authorize("update", "post", post);  // то же, но бросает исключение вместо false
```

Нет состояния, нет мутаций, а `ability.rules` — тот самый массив правил, из которого он собран: сериализуйте и отправляйте клиенту.

## Что у него есть

| Метод | На что отвечает |
|---|---|
| `can` / `cannot` | можно ли выполнить действие — с конкретной строкой или без неё |
| `authorize` | то же, что `can` со строкой, но бросает `ForbiddenError`; без строки не гадает |
| `canMutate` | можно ли писать в эту строку — см. [запись](./mutations.ru.md) |
| `validatePayload` | можно ли записать *именно эти данные* |
| `permittedFields` | какие поля можно редактировать |
| `where` | условие для запроса к базе — см. [фильтрация](./where.ru.md) |
| `validate` | подходят ли входящие данные под схему ресурса |
| `rules` | исходный массив, обычный JSON |

## Одно решение, три способа его сообщить

Когда строка передана, `can`, `cannot` и `authorize` проверяют **одно и то же**. Отличается только способ ответа — берите тот, что удобнее в конкретном месте:

```ts
if (ability.can("update", "post", post)) { … }                  // логическое значение, для ветвления
if (ability.cannot("update", "post", post)) return notFound();  // ранний выход
ability.authorize("update", "post", post);                      // исключение, на границе
```

`authorize` избавляет от `if (!can(…)) throw new ForbiddenError(action, resource)` и гарантирует, что все отказы выглядят одинаково.

## Настоящее различие: со строкой или без

Эта ось не зависит от трёх предыдущих — и именно она меняет сам вопрос.

**Со строкой** ответ точный: условия вычисляются по ней.

**Без строки** ответ оптимистичный — *может ли это быть разрешено хоть для какой-то строки?* Именно это нужно интерфейсу, когда вы решаете, рисовать ли кнопку, а проверять ещё нечего. Ответ будет «да», если действие покрыто хоть одним `allow` и его не перекрывает безусловный `deny`.

```ts
ability.can("create", "post");        // показывать кнопку «Новый пост»?
ability.can("update", "post", post);  // включать «Изменить» на этой строке?
```

`authorize` тоже принимает обе формы, но без строки оптимистом не становится. Он пропускает, только если никакая строка не изменила бы ответ: действие покрыто `allow` без `where`, и ни один `deny` строку не читает. Этого и ждёт route handler, проверяющий «а можно ли этому пользователю вообще создавать посты», — и поэтому тот же вызов откажет тому, кому разрешено менять только свои посты:

```ts
// allow("create", "post"), allow("update", "post", { where: { authorId: user.id } })
ability.authorize("create", "post");        // пропускает
ability.authorize("update", "post");        // бросает — какой именно пост?
ability.authorize("update", "post", post);  // точный ответ
```

> **`can` без строки отвечает на более слабый вопрос, и ничто не помешает применить его по ошибке.** Если операция работает с конкретной строкой — передайте её: `can("update", "post")` вернёт `true` пользователю, которому можно менять *какой-то* пост, но не этот.

## Как поймать отказ

```ts
import { ForbiddenError } from "@vetojs/core";

try {
	ability.authorize("delete", "post", post);
} catch (error) {
	if (ForbiddenError.is(error)) {
		error.action;     // "delete"
		error.resource;   // "post"
		error.violations; // заполнено только при отказе по данным
	}
}
```

Удобно в route handler или server action, где обработчик ошибок фреймворка превратит исключение в 403.

Используйте `ForbiddenError.is`, а не `instanceof`. Если в дереве зависимостей окажутся две копии `@vetojs/core`, у ошибки будет две идентичности класса, и `instanceof` ответит `false` на совершенно законный отказ — 403 тихо превратится в 500. За `is` стоит зарегистрированный символ, и его такая ситуация не смущает.

## Наблюдать за решениями

Передайте `onDecision` — и каждый ответ приедет данными: что спросили, что
ответили и какое правило это решило:

```ts
const ability = buildAbility(ac, policyFor(currentUser), {
	onDecision: (decision) => {
		log.info({
			actor: currentUser.id,
			action: decision.action,
			resource: decision.resource,
			allowed: decision.allowed,
			rule: decision.rule,
		});
	},
});
```

Пользователя в отчёте нет, и он там не нужен: ability принадлежит одному
пользователю, поэтому он уже есть в замыкании самого хука.

В `rule` лежит сработавший `deny` или разрешивший `allow`; поля нет вовсе,
когда не совпало ничего и отказал дефолт, — а это как раз случай, на который
стоит слать алерт: политика промолчала о вопросе, который кто-то задал.
Его нет и тогда, когда решающий вызов без ряда отказал, потому что ответ
зависел от ряда: условие говорит о ряде, и без него ни одно правило не отказало.
Запрет, сработавший на данных, которые он не смог сравнить в переданном ряду,
называется: ряд был, и запрет его прочитал.

Хук вызывается для `can`, `cannot`, `authorize`, `canMutate` и
`validatePayload`, по одному разу на вызов. У решения по payload правила в отчёте
нет: отказ там решается поле за полем — вместо правила приезжают `violations`, тот
же список, что возвращает вызов. Именно он отличает в журнале попытку подмены от
обычного отказа: `{ field: "authorId", reason: "field not permitted" }` говорит, что
кто-то пытался записать чужое поле. **Пустой** список `violations` — это тоже
отказ: запись отклонена целиком, общим `deny` или за отсутствием `allow`, и
называть было нечего. Для `where`, `permittedFields` и
`validate` — нет: они спрашивают, что говорит политика, а не можно ли
пользователю действовать.

Вердикт вычисляется до хука, поэтому повлиять на ответ хук не может. А вот
**бросок** из него — другое дело: вызов на этом останавливается, и вместо
ответа вашему вызывающему уходит ваше же исключение. Так ни один из перечисленных
вызовов не отдаёт разрешение, записать которое не удалось. Ловите внутри своего хука, если телеметрия не
должна ронять проверку:

```ts
const ability = buildAbility(ac, policyFor(currentUser), {
	onDecision: (decision) => {
		try {
			log.info(decision);
		} catch (error) {
			console.warn("veto: decision hook failed", error);
		}
	},
});
```

Ни строки, ни данных в отчёте нет. Имена полей есть, значений нет: журналу
решений они по умолчанию не нужны. И то и другое доступно там, где вы пишете
хук, — понадобятся, замкните их сами.

## `permittedFields` — для форм

```ts
ability.permittedFields("update", "post", ["title", "status", "views"]);
// → ["title", "status"]
```

Список полей приходится передавать самому: у схемы нельзя спросить её ключи — `shape<T>()` стирается при сборке, а Standard Schema их не перечисляет.

Это нужно интерфейсу. На сервере всё равно отработает `validatePayload`: заблокированное поле ввода — вежливость, а не защита.

## `validate` — про форму данных, а не про права

```ts
const result = ability.validate("post", input);
if (!result.ok) return badRequest(result.issues);
// result.value — проверенные данные с уточнённым типом
```

Это вторая половина работы с недоверенным вводом. `validate` отвечает на вопрос *а это вообще корректный пост?*, `validatePayload` — *можно ли этому пользователю такое записать?* Вместе и именно в таком порядке они дают полную картину.

У каждой проблемы есть `message` от самой схемы и `path` — поле, на которое она указала: `["authorId"]` или `["meta", "views"]` для вложенного, — так что и журнал, и форма знают, куда показывать. `path` отсутствует, когда схема ругается на значение целиком.

Метод запускает схему ресурса, так что реальную работу делает только тогда, когда в `defineAbilities` передана настоящая Standard Schema (Zod, Valibot, ArkType). Пустышка `shape<T>()` по-прежнему отсеет не-объект, но поля проверить не сможет. Асинхронные схемы не поддерживаются: если `validate` вернёт промис, будет исключение — а значит, Yup не подойдёт, он реализует стандарт только асинхронно. См. [как подставить настоящую схему](./define-abilities.ru.md#подставить-настоящую-схему-вместо-typet).

Неизвестный ресурс не проходит насквозь, а отклоняется, как и положено проверке на границе.

## Типы подсказывают, защищает движок

Аргументы методов типизированы: редактор подсказывает, а опечатки не компилируются. Но такая типизация выражает *намерение*, и безопасность держится не на ней.

Держится она на тотальности движка: не-объект получает отказ, поле неверного типа даёт «неизвестно», и в обе стороны это играет на запрет. Поэтому строка, не совпавшая с объявленной формой, приведёт разве что к *лишним* отказам — но не к падению и не к выдаче доступа.

Если данные непроверенной формы всё же нужно пропустить, возьмите подходящую проверку вместо приведения `as unknown as`:

| Данные | Проверка |
|---|---|
| JSON с правилами из базы или по сети | [`parseRules(json, ac)`](./parse.ru.md) |
| строка или payload непроверенной формы | `ability.validate(resource, data)` |

## Правила, которых нет в ваших объявлениях

`buildAbility` не бросает исключений, не отбрасывает такие правила и не предупреждает о них: к этому моменту они уже доверенные, поскольку проверка прошла раньше — при компиляции через `createRules` либо во время работы через `parseRules`. По той же причине `buildAbility` и принимает только проверенные правила — см. [правила извне](./parse.ru.md).

## Почему так устроено

- **Обычные данные и замыкания, никаких классов.** При сериализации нечего обходить, мутировать нечего, собирать на каждый запрос в серверном компоненте безопасно.
- **`authorize` ничего не возвращает.** Это охрана, а не преобразователь: переданная строка и так уже типизирована.
- **`authorize` без строки отказывает там, где решить могла бы только строка.** Он стоит там, где операция вот-вот случится, и «разрешено для какой-то строки» — не повод её пропускать. `can` без строки остаётся оптимистом: спрятанная кнопка — вежливость, а проверка всё равно на сервере.
- **`canMutate` и `validatePayload` принимают частичную строку**: у кандидата на вставку ещё нет ни `id`, ни `createdAt` из базы, а требование полной строки заставляло бы приводить типы при каждом создании.
- **`ability.rules` — это и есть формат передачи.** Отправьте массив клиенту, передайте в `<AbilityProvider rules={…}>` — и интерфейс заживёт теми же правилами.
