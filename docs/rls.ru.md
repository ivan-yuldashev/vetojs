# Вместе с row-level security в Postgres

**[English](rls.md) · [Русский](rls.ru.md)**

RLS и эта библиотека отвечают на разные половины одного вопроса. Postgres решает, **какие строки видит соединение**. Veto решает то же самое — и вдобавок, какие поля можно писать, что рисовать в интерфейсе и до чего дотянется вызов инструмента агентом. Использовать оба разумно; считать, что один заменяет другой, — нет.

## Что умеет каждая половина

| | RLS | veto |
|---|---|---|
| Какие строки вернёт запрос | ✅ обеспечивает база | ✅ компилируется в `WHERE` |
| Какие поля можно писать | ✖ `GRANT UPDATE (col)` привязан к роли, а не к пользователю и строке | ✅ `fields` и ограничения значений |
| Гейтинг интерфейса | ✖ в браузер ничего не уезжает | ✅ правила едут как JSON |
| Ресурс без таблицы | ✖ политику вешать не на что | ✅ обычное правило |
| Что-либо кроме Postgres | ✖ | ✅ |

Осмысленная пара: **RLS как пол, veto как контракт.** База отказывается отдавать строки, даже если запрос забыл фильтр; приложение по-прежнему объясняет, *почему*, и отклоняет запись по полям.

## Три способа считать себя защищённым, не будучи им

**Владелец таблицы обходит RLS.** Включение row security ничего не даёт роли, которой таблица принадлежит, — а приложение подключается владельцем сплошь и рядом. Симптом худший из возможных: каждый запрос возвращает все строки, молча.

```sql
alter table posts enable row level security;
alter table posts force  row level security;
```

Без `force` соединение-владелец видит всё.

**Сессионная настройка вне транзакции ни к чему не привязана.** `SET LOCAL` живёт внутри текущей транзакции, обычный `SET` — внутри соединения, а за пулером это соединение следующего запроса. Ставьте пользователя на транзакцию и читайте его в политике:

```sql
begin;
set local "veto.actor" = 'u1';
-- запросы здесь
commit;
```

**Политики по умолчанию складываются через OR.** Каждая добавленная `PERMISSIVE` политика **расширяет** доступ. Это противоположность модели с приоритетом запрета: запрет обязан быть написан `AS RESTRICTIVE`, и одно забытое слово превращает его в пустое место.

## Как писать выражение политики

Условие, которое компилирует veto, уже нужной для `USING` формы — тотальное, никогда не `NULL`, со связями через `EXISTS`, — но собрано оно **под одного пользователя**, и его значения переданы параметрами. Политика — это DDL, пользователя у неё нет, поэтому значение должно приходить из сессии:

```
using ("posts"."author_id" is not distinct from current_setting('veto.actor', true))
```

Вся разница в этой подстановке — и именно поэтому генератору политик нужны шаблонные правила, а не те, что мы собираем сегодня под конкретного актора.

## Чем это оплачивается

Политика — это DDL, сгенерированный один раз. Правила приложения — код, который выкатывают постоянно. **Они разъезжаются**, и никто об этом не сообщит: гарантия, на которой стоит библиотека («фильтр отбирает ровно то, что разрешает `can()`», доказуемо на каждом запросе), превращается в «накатанная политика совпадает с кодом» — а это уже вопрос миграций, а не теста.

Поэтому: держите RLS как пол, ловящий забытый фильтр, храните политику в одном месте и не заводите два источника правды для одного правила, если этого можно избежать.

## Почему так устроено

- **База — единственное место, где забытый фильтр не может утечь.** Это ценно даже при аккуратном приложении.
- **У правил на поля и на интерфейс аналога в базе нет**, поэтому убрать veto из стека — значит убрать эти два, а не просто снять дублирование.
- **Двузначность предикатов важна и здесь.** `NOT` над `NULL` в выражении `USING` тихо переворачивает видимость строки — тот самый класс ошибок, который [адаптер Drizzle](./drizzle.ru.md) отказывается выпускать.
