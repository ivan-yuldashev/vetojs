# `@vetojs/react` — политика в интерфейсе

**[English](react.md) · [Русский](react.ru.md)**

Те же правила, что защищают сервер, решают и что доступно пользователю в интерфейсе. Правила приезжают на клиент плоскими данными, а читают их три привязки.

```sh
npm install @vetojs/react @vetojs/core
```

React 18 и новее. `@vetojs/core` — peer-зависимость: приложение резолвит его один раз, и привязки работают с той же копией.

## Один раз создайте привязки

`createVetoContext(ac)` запоминает ваши объявления и возвращает привязки, которые знают о ваших ресурсах. Сделайте это в одном модуле и импортируйте оттуда:

```ts
// src/authz.ts
import { createVetoContext } from "@vetojs/react";
import { ac } from "./abilities";

export const { AbilityProvider, useAbility, Can } = createVetoContext(ac);
```

Шаг этот нужен потому, что обычный импорт не принесёт с собой тип вашего `ac`, а фабрика — принесёт. Взамен `<Can>` подсказывает действия для каждого ресурса и не пропускает несуществующие.

### Не пускайте карту ресурсов в свой `.d.ts`

Если модуль входит в публикуемый пакет, аннотируйте экспорт. TypeScript сохраняет
именованный псевдоним только там, где псевдоним написан в самом объявлении, поэтому
деструктуризация печатает всю карту ресурсов в выходные типы — по копии на каждую привязку:

```ts
export type AC = typeof ac;

const veto: VetoContext<AC> = createVetoContext(ac);

export const AbilityProvider: VetoContext<AC>["AbilityProvider"] = veto.AbilityProvider;
export const Can: VetoContext<AC>["Can"] = veto.Can;
export const useAbility: VetoContext<AC>["useAbility"] = veto.useAbility;
```

Замерено на объявлении из 25 ресурсов: деструктуризация даёт 28.6 kB деклараций,
аннотация — 5.1 kB. Одного `type AC = typeof ac` недостаточно: псевдоним должен стоять в
объявлении, которое им пользуется. Реэкспорт члена без типа снова разворачивает карту.

## Передайте ability вниз

Оберните дерево один раз, поближе к корню:

```tsx
<AbilityProvider rules={rules}>
	<App />
</AbilityProvider>
```

`rules` — обычный массив из `ability.rules`, ровно то, что прислал сервер. Провайдер сам соберёт ability и запомнит результат, так что перерисовка политику не пересоберёт.

Если ability на клиенте у вас уже есть, передайте его:

```tsx
<AbilityProvider ability={ability}>
```

Эти два свойства взаимоисключающие: передать оба не даст типизация.

> Правила, пришедшие с сервера, — такой же недоверенный ввод, как и любой другой. Проверяйте их на границе через [`parseRules`](./parse.ru.md) — провайдер и принимает только проверенные правила именно поэтому.

**Правила не референсно стабильны.** Функция политики создаёт новые объекты правил на
каждый вызов, а провайдер пересобирает ability, как только у пропа `rules` меняется
идентичность. Поэтому селектор вида `useStore(useShallow((s) => policyFor(s.user)))` не
стабилизируется никогда — каждый рендер даёт новый массив. Мемоизируйте по пользователю
или проталкивайте правила через
 [`useSetRules`](#usesetrules--переключить-пользователя-без-перерисовки-страницы).

## `<Can>` — показать, если можно

```tsx
<Can I="update" a="post" this={post}>
	<EditButton />
</Can>
```

Читается как фраза: *я* могу **обновить** *пост*, вот этот. Без `fallback` при отказе не отрисуется ничего, с ним — можно показать неактивное состояние:

```tsx
<Can I="update" a="post" this={post} fallback={<DisabledButton />}>
	<EditButton />
</Can>
```

Уберите `this`, если строки ещё нет: для кнопки «Новый пост» вопрос лишь в том, доступно ли действие в принципе:

```tsx
<Can I="create" a="post">
	<NewPostButton />
</Can>
```

Всё сверяется с вашими объявлениями:

```tsx
<Can I="archive" a="post">   {/* ✗ у "post" нет действия "archive" */}
<Can I="update" a="posts">   {/* ✗ такого ресурса нет */}
<Can I="update" a="post" this={user}>  {/* ✗ форма не подходит под "post" */}
```

## `useAbility` — для всего остального

Для списков, неактивных состояний и любых проверок, которые не сводятся к «рисовать или нет»:

```tsx
const ability = useAbility();

const visible = postList.filter((post) => ability.can("read", "post", post));
const writable = ability.permittedFields("update", "post", post, ["title", "status"]);

<input disabled={!writable.includes("title")} />
```

Хук возвращает [`ability`](./ability.ru.md) целиком — доступны `can`, `cannot`, `permittedFields` и всё остальное. Вне провайдера он сразу бросает исключение, а не притворяется молча, что ничего не разрешено.

## `useCan` — один вопрос, одна подписка

`useAbility` отдаёт объект целиком, поэтому каждый держащий его компонент просыпается при любой смене правил. `useCan` подписывается на **один** вердикт и перерисовывает компонент, только когда меняется именно этот ответ:

```tsx
const canEdit = useCan("update", "post", post);
```

На списке из 50 закрытых строк, где смена пользователя меняет ровно один вердикт, `useAbility` перерисует все 50, а `useCan` — одну. `<Can>` пользуется им внутри, так что ведёт себя так же. `useAbility` берите там, где нужен не только ответ «да/нет»: `permittedFields`, `validate`, фильтрация по многим строкам.

## `useSetRules` — сменить пользователя, не перерисовывая страницу

Передать провайдеру новые `rules` можно, но это идёт через состояние React у предка, а значит предок перерисуется и утянет за собой всё поддерево. На том же списке из 50 строк это 101 перерисовка на один изменившийся вердикт — и ни одна из них не от `<Can>`, это обычное распространение сверху вниз.

`useSetRules` пишет в стор напрямую:

```tsx
const setRules = useSetRules();

const onSwitchActor = async (id: string) => {
	const { rules } = await fetchActor(id);
	setRules(rules);
};
```

Выше не перерисовывается ничего — ни провайдер, ни список, — а обновляются только строки с изменившимся вердиктом. Измерено на том же списке: провайдер 0, незакрытые строки 0, закрытые 1.

Проп `rules` используйте, чтобы засеять дерево данными с сервера, а `useSetRules` — для смен, которые происходят без нового запроса.

## Экраны и вкладки — ресурсы без строк

Экран аналитики, вкладка биллинга, страница настроек: существительные вашего словаря, за которыми нет и не будет таблицы. Объявляются они как всё остальное, а «строкой» для них служит то, что определяет *этот* экран, — обычно параметры маршрута.

```tsx
const ac = defineAbilities({
	resources: {
		analytics: {
			schema: shape<{ workspaceId: string }>(),
			actions: ["view"],
		},
	},
});

const { allow } = createRules(ac);
const { Can } = createVetoContext(ac);

const rules = [
	allow("view", "analytics", { where: { workspaceId: { in: ["w1"] } } }),
];

const AnalyticsTab = ({ workspaceId }: { workspaceId: string }) => (
	<Can I="view" a="analytics" this={{ workspaceId }} fallback={<Forbidden />}>
		<AnalyticsPanel />
	</Can>
);
```

**Если у экрана есть параметр, передавайте `this`.** Опустить его уместно для кнопки «Новый пост», где строки ещё нет, и неуместно здесь: ответ без строки оптимистичен — истина, когда действие *могло бы* быть разрешено для какой-то строки, — и вкладка появится в каждом воркспейсе, включая те, которых правило не называет. Параметр и есть строка, отдайте её.

Правило остаётся правилом: `deny` по-прежнему перебивает, а смена параметра маршрута заново отвечает на вопрос — та же политика прячет аналитику одного воркспейса и показывает другого, без второй ветки кода.

Экрану, у которого ключа нет вовсе — один отчёт, одна страница настроек, — форма не нужна совсем, и `schema` в его объявлении не пишут. У этого есть воркспейс, значит есть и строка.

Таблицы у такого ресурса нет, и об этом говорят обе стороны: адаптеру — через [`defineTables(ac, { analytics: null })`](./drizzle.ru.md#ресурсы-без-таблицы), а сервер просто проверяет `can("view", "analytics", { workspaceId })` там, где рисует страницу, потому что фильтровать нечего. О чём и следующий раздел.

## Спрятать — не значит защитить

Скрытая кнопка — вежливость к пользователю, а не граница безопасности: запрос, который она бы отправила, ничто не мешает отправить руками. Каждое действие всё равно нужно проверять на сервере:

- строки — фильтруйте в базе через [`ability.where`](./where.ru.md);
- изменения — закрывайте через [`canMutate` / `validatePayload`](./mutations.ru.md).

Смысл общего массива правил в том, что обе стороны читают один источник, и интерфейс не разойдётся с тем, что на самом деле разрешит сервер.

## Серверные компоненты

**На сервере ничего из перечисленного выше не нужно.** Ни контекста, ни провайдера, ни клиентской границы: ability у вас уже есть — просто спросите его.

```tsx
import { Can } from "@vetojs/react/server";

const ability = await getAbility();
if (!ability.can("read", "post", post)) notFound();

return (
	<Can ability={ability} I="update" a="post" this={post} fallback={<ReadOnly />}>
		<EditForm post={post} />
	</Can>
);
```

У этого `<Can>` нет ни `"use client"`, ни единого хука. Обе ветки решаются во время рендера, поэтому **в браузер не уезжает ни одна** — клиент получает только готовый результат. Фабрика тоже не нужна: схема ресурсов выводится из переданного ability, так что действия по-прежнему сверяются с ресурсом прямо при наборе.

Собирайте ability один раз на запрос, а не в каждом компоненте. В Next для этого есть `cache` из React:

```ts
export const getAbility = cache(async () =>
	buildAbility(ac, policyFor(await getActor())),
);
```

К клиентским привязкам обращайтесь только там, где интерфейс должен **реагировать**: оптимистичное переключение, смена роли — всё, что меняется без нового запроса. Тогда передайте правила через границу:

```tsx
<AbilityProvider rules={ability.rules}>
	<Toolbar post={post} />
</AbilityProvider>
```

Через границу едет только массив правил — обычный JSON, при сериализации обходить нечего. Именно это и делает всю схему возможной: ability здесь — данные и замыкания, а не экземпляр класса. Ability на классе такую границу не пересекает, и на этом заканчивается дорога у библиотек, построенных на классах.

## Почему так устроено

- **Фабрика, а не глобальный объект.** Типизированным привязкам нужен ваш `ac`, а модульный импорт его не получит. Один локальный модуль с реэкспортом трёх привязок держит остальной код чистым.
- **Либо `rules`, либо `ability`, но не оба сразу.** С сервера приходят данные, а на клиенте ability может уже существовать. Разреши мы оба — сразу встанет вопрос, что главнее.
- **`useAbility` без провайдера бросает исключение.** Вернуть ability, который всё запрещает, значило бы выдать ошибку подключения за решение политики.
- **`<Can>` рисует либо `children`, либо `fallback`, и ничего сверх того.** Никакой обёртки — поэтому он спокойно встраивается во flex- и grid-раскладки.
- **Две точки входа, потому что `"use client"` помечает модуль целиком.** Быть обоими сразу модуль не может, поэтому серверный компонент живёт в `@vetojs/react/server` и не делит с клиентским ничего, кроме типа. Альтернатива — один клиентский `<Can>` повсюду — и есть та причина, по которой серверный компонент приходится делать клиентским ради того, чтобы спрятать кнопку.
- **Клиентский `<Can>` тоже принимает `ability` пропом.** Передали — контекст игнорируется; это выход, когда у поддерева свой ability или когда провайдер вешать не хочется. Если нет ни того ни другого, компонент бросает исключение, а не додумывает.
