# Правила извне — `parseRules`

**[English](parse.md) · [Русский](parse.ru.md)**

Правила из базы, из админки или от модели — недоверенный ввод. `parseRules` проверяет их форму, прежде чем их примет `buildAbility`:

```ts
import { buildAbility, parseRules } from "@vetojs/core";

const result = parseRules(JSON.parse(raw));

if (!result.ok) {
	throw new Error(result.errors.join("\n"));
}

const ability = buildAbility(ac, result.rules);
```

Он не бросает исключение, а возвращает все проблемы, каждую с путём:

```
rules[1].where.or[0].op: unknown operator "regex"
rules[2].effect: expected "allow" | "deny"
```

В обратную сторону API не нужен: `JSON.stringify(ability.rules)`.

## Что проверяется

- массив объектов-правил, `effect` — ровно `"allow"` или `"deny"`;
- `action` — непустое имя или список имён, `resource` — непустое имя;
- условия правильно устроены: известные операторы, у каждого значение, которое он умеет сравнить, — массив для `in`, `nin`, `hasAny`, `hasAll`, булево для `exists`, строка для `contains`, число или строка для `gt`, `gte`, `lt`, `lte`; `ref` только в `where` и только под `eq ne gt gte lt lte`; группы хотя бы с одним условием; связи правильной формы; ровно одна форма на узел;
- `fields` — непустой список непустых имён, `values` — плоское, `when` — без связей;
- ключа `payload` нет — он был у правил, написанных для старой сборки.

Каждый ключ читается как собственное свойство, так что загрязнённый `Object.prototype` ничего к правилу не добавит.

## Имена не проверяются

`parseRules` не знает ваших объявлений. Правильно устроенное правило, которое называет что-то, чего нет в этой сборке, проходит:

| Правило называет | При проверке |
|---|---|
| незнакомый ресурс или действие | ничему не соответствует — `allow` ничего не разрешает, `deny` ничего не запрещает |
| незнакомую связь | бросает `RelationNotLoadedError`, когда до неё доходит |

Генерируйте хранимые правила из тех же объявлений, что читает сборка: `createRules(ac)` отвергает незнакомые имена ещё при компиляции. См. [правила в виде JSON](./for-agents.ru.md#правила-в-виде-json).

## Пропустить проверку непросто

`buildAbility` принимает только правила из `createRules` или `parseRules`:

```ts
import { buildAbility, type Rule } from "@vetojs/core";

declare const stored: Rule[];
buildAbility(ac, stored); // ✗ не проверены
```

`buildAbility(ac, JSON.parse(raw))` при этом компилируется: `any` отменяет любые типы. Пропускайте недоверенный JSON через проверку потому, что он недоверенный, а не потому, что вас остановит компилятор. Правило, прошедшее через `JSON.parse`, должно пройти проверку заново.

## Почему так устроено

- **Результат, а не исключение.** Плохие данные в хранилище — ожидаемая ситуация, а редактору или миграции нужны все ошибки сразу.
- **Разрешает только точное `"allow"`.** `"Allow"` или опечатку отвергает проверка, и движок тоже не прочитает их как разрешение.
- **Без библиотеки схем.** Проверки, написанные руками, избавляют движок от зависимостей.
