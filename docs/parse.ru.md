# Правила извне — `parseRules`

**[English](parse.md) · [Русский](parse.ru.md)**

То, что правила — обычный JSON, делает их удобными для хранения и передачи. Оно же делает их опасными на обратном пути: JSON из базы, из админки или по сети — это недоверенный ввод. `parseRules` — дверь, через которую он обязан пройти.

```ts
import { buildAbility, parseRules } from "@vetojs/core";

const result = parseRules(JSON.parse(raw), ac);

if (!result.ok) {
	throw new Error(`Invalid rules:\n${result.errors.join("\n")}`);
}

const ability = buildAbility(ac, result.rules);
```

Функция возвращает результат, а не бросает исключение: падать, писать в лог или подставлять запасную политику — решать вам.

В обратную сторону никакого API не нужно: `JSON.stringify(ability.rules)`.

## Почему это защита, а не формальность

Движок считает разрешением любой `effect`, кроме `deny`. А значит, один испорченный символ в сохранённом JSON тихо превратит запрет в разрешение. То же самое — с незнакомым оператором или с `in`, у которого список оказался не списком.

Проверка формы на входе снимает весь этот класс проблем.

## Что проверяется

Рекурсивно, с накоплением **всех** проблем сразу, а не с остановкой на первой, и с путём до каждой:

```
rules[1].where.or[0].op: unknown operator "regex"
rules[2].effect: expected "allow" | "deny"
```

- на верхнем уровне массив объектов;
- `effect` — ровно `allow` или `deny`;
- `action` — строка или массив строк, `resource` — строка;
- `where`, если есть, — корректное условие: известные операторы, настоящие массивы у `in`/`nin`, связи правильной формы `one`/`many`;
- у каждого узла условия **ровно одна** форма: узел, назвавший сразу `and` и `field`, отклоняется — и в `where`, и в `payload.constraints`;
- `payload`, если есть, — строковые `fields` и плоские `constraints`.

## Имена, которых здесь не знают

Проверка формы не поймает правило, написанное верно, но упоминающее то, чего в этой сборке нет: `resource: "psot"` или действие из более новой версии схемы во время постепенного выката.

Эти два случая несимметричны:

- незнакомый **allow** ничего не даёт и сам по себе безобиден;
- незнакомый **deny** — это *защита, которой тихо нет*, и вот он уже опасен.

Поэтому, если передать свои объявления как словарь, эти два случая обрабатываются по-разному:

| Правило с незнакомым именем | Что происходит | Почему |
|---|---|---|
| `allow` | **в карантин** — попадает в отчёт, но не применяется | оно не должно давать доступ к тому, чего в этой сборке нет |
| `deny` | **остаётся** и попадает в отчёт | он обязан продолжать защищать; убрать его — только расширить доступ |

```ts
const result = parseRules(json, ac);
if (!result.ok) throw new Error(result.errors.join(", "));

result.unknown; // [{ rule, reasons, quarantined }]
```

**`parseRules(json, ac)` и `parseRules(json, toVocabulary(ac))` взаимозаменяемы.** Гейт читает только имена действий и связи, а объявление ресурса — это запись словаря с приложенной схемой, поэтому оба вызова отвечают одинаково. Предпочитайте `toVocabulary(ac)`, когда словарь хранится: это сериализуемая половина без схем, и именно она лежит в базе рядом с правилами.

Что делать с `unknown` — решаете вы; на каждый случай по строке:

```ts
expect(result.unknown).toEqual([]);          // в CI опечатка должна ронять сборку
if (result.unknown.length) log.warn(...);    // в проде расхождение версий — это телеметрия
```

**Проверка способна только сузить доступ.** Отбрасывая разрешения и сохраняя запреты, она никогда не превратит запрещённый вызов в разрешённый, поэтому выкат, где база опережает код, безопасен по построению. Это подтверждено property-тестом, а не просто заявлено.

Имена полей намеренно **не** проверяются: Standard Schema не перечисляет свои ключи, а движок и без того считает отсутствующее поле определённым несовпадением.

## Проверку нельзя забыть

`buildAbility` не принимает голый `Rule[]` — только правила, о которых доказано, что проверку они прошли. Мест таких ровно два:

1. `createRules(ac)` — проверил компилятор;
2. `parseRules(input, vocabulary)` — проверила эта дверь.

```ts
const rules: Rule[] = load();
buildAbility(ac, rules);                                 // ✗ не проверены
buildAbility(ac, parseRules(JSON.parse(raw), ac).rules); // ✓
```

Одна оговорка, о которой стоит знать: `JSON.parse` возвращает `any`, а `any` обходит любую типизацию. Поэтому `buildAbility(ac, JSON.parse(raw))` всё-таки скомпилируется. Метка ловит то, что вообще способны поймать типы, — литерал, написанный руками, или обычный `Rule[]`, — но не значение, которое свой тип уже потеряло. Пропускайте недоверенный JSON через проверку потому, что он недоверенный, а не потому, что компилятор вас остановит.

Метка живёт только на уровне типов (правила остаются обычным JSON без лишних свойств) и намеренно не переживает `JSON.parse`. Разобранные из JSON правила обязаны пройти проверку заново — в этом и смысл.

Вызов `parseRules` *без* словаря проверяет только форму и возвращает непомеченные правила, поэтому `buildAbility` их не примет. Запасной выход, если вы правда этого хотите (например, собираете заведомо сломанные правила в тесте), — заметное приведение `as CheckedRules`.

## Почему так устроено

- **Объект-результат вместо исключения.** Плохие данные здесь — ожидаемая ситуация, а не исключительная.
- **Все ошибки сразу и с путями.** Редактору в интерфейсе или скрипту миграции нужен полный список, а не остановка на первой же.
- **Любое имя ищется как собственное свойство**, так что подделанные `op`, `resource`, `field` или `relation` с именем `constructor` или `toString` ни до чего не дотянутся через цепочку прототипов: операторы сверяются со списком допустимых значений, а ресурсы и связи читаются через `Object.hasOwn`.
- **Никакой библиотеки схем.** Написанная руками рекурсия оставляет движок без зависимостей и не привязывает формат правил к чужому валидатору.
