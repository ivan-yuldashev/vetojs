# Операторы условий

**[English](operators.md) · [Русский](operators.ru.md)**

Любое условие в правиле упирается в сравнение: *равно ли поле такому-то значению, больше ли, входит ли в список?* Операторов тринадцать, и здесь разобран каждый — вместе с неудобными случаями (`null`, неверный тип, `NaN`), где ошибка обернулась бы тихой выдачей доступа.

Операторы пишут короткой записью:

```ts
allow("read", "post", { where: { status: "published" } });        // eq, неявно
allow("read", "post", { where: { views: { gte: 100 } } });        // явный оператор
allow("read", "post", { where: { status: { in: ["draft", "review"] } } });
```

## Тринадцать операторов

| Оператор | Истинно, когда | Примечания |
|---|---|---|
| `eq` | значения равны | `Date` сравнивается по метке времени (в том числе с числом миллисекунд), `1` равно `1n`; в остальном строгое `===`. Строки — с учётом регистра; объекты и массивы дают **«неизвестно»**, а не равенство или неравенство |
| `ne` | не `eq` | |
| `in` | значение есть в списке | вхождение проверяется тем же равенством, что и `eq` |
| `nin` | значения нет в списке | |
| `gt` `gte` `lt` `lte` | сравнение по порядку | числа, bigint, даты или строки |
| `contains` | строка содержит подстроку | только для строк, с учётом регистра |
| `exists` | наличие совпадает с тем, о чём спросили | принимает только `true` или `false`; `exists: true` — не `null` и не `undefined`; `0`, `false` и `""` считаются присутствующими |
| `has` | массив содержит элемент | только поля-массивы скаляров |
| `hasAny` | массив содержит хотя бы один из списка | краткая запись `or` над `has` |
| `hasAll` | массив содержит каждый из списка | краткая запись `and` над `has`; пустой список ничего не требует от элементов, поэтому ему удовлетворяет любой массив — но не отсутствующее поле |

## Когда значения не сходятся

Живые данные бывают грязными: в колонке `NULL`, в JSON приходит `"5000"` вместо числа, правило из базы тащит сломанный список. На этот случай у каждого оператора три возможных ответа:

- **да** / **нет** — определённый ответ;
- **неизвестно** — данные и условие несовместимы, и честного «да» или «нет» тут просто не существует.

«Неизвестно» — не формальность, а защитный механизм. На таком ответе `allow` не даёт ничего, а `deny` **всё равно срабатывает**. В обе стороны это играет на запрет, поэтому испорченные данные способны только сузить доступ. (Как три состояния складываются — в разделе [как принимается решение](./rule-evaluation.ru.md).)

Откуда берётся тот или иной ответ:

| Ситуация | Ответ | Почему |
|---|---|---|
| Поле `null` или отсутствует, а оператор `gt` / `lt` / `contains` | **нет** | «значения нет» заведомо ничего не превышает |
| `views > "abc"` — число против строки | **неизвестно** | между ними нет осмысленного порядка |
| `NaN` или некорректная `Date` | **неизвестно** | по нему нечего упорядочивать, сравнение ничего не решает |
| `status in "draft"` — список не список | **неизвестно** | правило сломано; см. ниже |
| Оператор, которого движок не знает | **нет** | сломанные правила запрещают, а не роняют приложение |

### Подробности про порядок

Перед сравнением операнды приводятся к общему виду: числа, bigint и строки берутся как есть, а `Date` превращается в метку времени — поэтому дата и число миллисекунд для движка одно и то же. Сравнение состоится, только если обе стороны числовые либо обе строковые; во всех прочих случаях — «неизвестно».

### Почему `nin` на сломанном списке даёт «неизвестно», а не «да»

Если бы на сломанном списке `in` отвечал простым **нет**, то `nin` — его отрицание — ответил бы **да**, и сломанное правило принялось бы выдавать доступ. «Неизвестно» — единственный ответ, который остаётся безопасным после отрицания. (`parseRules` отсеивает такие правила ещё на границе доверия, так что здесь это вторая линия обороны.)

## Почему так устроено

- **Сравнения не бросают исключений и ничего не приводят к другому типу.** Postgres спокойно сравнил бы `'200'` с `200`, а JavaScript сопоставил бы `"10" < "9"` как строки. Движок не делает ни того ни другого: значение неверного типа даёт «неизвестно», а не молчаливое совпадение.
- **`Date` и число взаимозаменяемы.** В правилах дата хранится числом миллисекунд, чтобы пережить `JSON.stringify` (см. [короткую запись](./condition-shorthand.ru.md)), но и сравнение с настоящей `Date` из ORM работает: оба представления сравниваются по значению.
- **`1` равно `1n`.** Числовые идентификаторы постоянно ходят между `number` и `bigint`, и считать их разными значило бы расставить ловушку. Сверяется точное значение, а не разрядность: `1.5` не равно ни одному bigint.
- **`exists` спрашивает про наличие, а не про истинность.** `0` и `""` — совершенно нормальные значения, и, посчитав их отсутствующими, движок отказывал бы настоящим строкам.
- **У поля-массива спрашивают про элементы, а не сравнивают его целиком.** `has` / `hasAny` / `hasAll` — единственные сравнения, доступные для такого поля, остальные убраны типами: `eq` по массиву мог бы отвечать только «неизвестно». Присутствующее не-массивное значение тоже даёт «неизвестно», поэтому на неверной форме ни одна полярность не решает; отсутствующее поле — разрешимое несовпадение. Postgres переводит все три в один индексируемый оператор, поэтому SQL и движок совпадают строка в строку.
- **Объект или массив в операнде — это «неизвестно», а не «не равно».** Операторы сравнивают значения, а два структурно одинаковых объекта — это разные ссылки, поэтому ответ «не равно» был бы догадкой под видом факта. Раньше здесь возвращалось `false`, и это тихо обезоруживало любой `deny` по такому полю: запрет не применялся ни к одной строке, что бы в ней ни лежало. «Неизвестно» — честный ответ, и он играет на отказ в обе стороны. Если нужно сопоставление внутри вложенного объекта, моделируйте его [связью](./relations.ru.md): движок сравнивает скаляры, а адаптер базы вообще откажется собирать запрос со сравнением объектов.
