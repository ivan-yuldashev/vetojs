# Условия

**[English](conditions.md) · [Русский](conditions.ru.md)**

`where` в правиле — это небольшое дерево: в листьях сравнения, между ними `and` / `or` / `not`, а узлы связей уводят в соседние ресурсы. Ниже — как это дерево вычисляется по строке.

Обычно условия пишут короткой записью, так что самого дерева вы не видите:

```ts
allow("update", "post", {
	where: {
		status: "draft",
		author: { id: actor.id },
		or: [{ views: { lt: 100 } }, { pinned: true }],
	},
});
```

Соседние ключи объединяются через **и**. В дерево короткая запись превращается прямо при создании правила, поэтому на хранение уходит обычный JSON — см. [короткую запись](./condition-shorthand.ru.md).

## Виды узлов

```ts
type ConditionNode<T> =
	| { field: keyof T; op: ConditionOperator; value: unknown }
	| { relation: string; type: "one" | "many"; match?: MatchQuantifier; where: ConditionNode<T> }
	| { and: ConditionNode<T>[] }
	| { or: ConditionNode<T>[] }
	| { not: ConditionNode<T> };
```

| Узел | Выполняется, когда |
|---|---|
| `field` | сравнение верно — см. [операторы](./operators.ru.md) |
| `relation` | связанные строки удовлетворяют вложенному условию — см. [связи](./relations.ru.md) |
| `and` | верны все потомки |
| `or` | верен хотя бы один потомок |
| `not` | внутренний узел неверен |

Пустой `and` выполняется — нарушать нечего; пустой `or` не выполняется — удовлетворять нечего. Поэтому `{ and: [] }` работает как узел «всегда», а `{ or: [] }` — как «никогда»; ими компилятор и выражает *нет ограничений* и *невозможно*.

## Три состояния, а не два

Кроме «да» и «нет» у узла есть третий ответ — **«неизвестно»**. Он появляется, когда данные несовместимы с условием: поле не того типа, испорченный элемент связи. Логические операции переносят это состояние по правилам трёхзначной логики:

| | результат |
|---|---|
| `and` | **нет**, если хоть один потомок «нет»; иначе **неизвестно**, если хоть один «неизвестно»; иначе да |
| `or` | **да**, если хоть один потомок «да»; иначе **неизвестно**, если хоть один «неизвестно»; иначе нет |
| `not` | меняет местами «да» и «нет», «неизвестно» оставляет как есть |

Главное — последняя строка: `not` не превращает «неизвестно» в «да». Значит, запрет, обёрнутый в отрицание, не обезоружить, подсунув мусор. Что движок делает с итоговым «неизвестно», описано в разделе [как принимается решение](./rule-evaluation.ru.md).

## Что может бросить исключение

Почти ничего. Вычисление синхронное, чистое и тотальное: незнакомый узел или неизвестный оператор приводят к отказу, а не к падению.

Единственное исключение — **связь, которая правилу нужна, но не загружена**. В этом случае поднимается `RelationNotLoadedError`: тихо засчитать отсутствие данных за «не совпало» — прямой путь к утечке строк. См. [связи](./relations.ru.md).

## Почему так устроено

- **Ветки распознаются по наличию ключа** (`"and" in node`) — так же, как устроено объединение на уровне типов. Побеждает первая названная форма, поэтому у узла она должна быть ровно одна: [`parseRules`](./parse.ru.md) отклоняет узел с двумя, иначе половина условия молча пропала бы. Узел, не подошедший ни под одну известную форму, уходит на вычисление оператора, а незнакомый оператор отвечает **«неизвестно»**: `allow` ничего не даёт, `deny` срабатывает.
- **Все ветки вычисляются, даже когда ответ уже ясен.** `deny` со сработавшей первой веткой всё равно обойдёт остальные: так незагруженная связь будет замечена в любом месте дерева, а не спрятана порядком вычисления. Диагностика остаётся предсказуемой, а цена — полный обход условий, в которых на практике два-три узла.
