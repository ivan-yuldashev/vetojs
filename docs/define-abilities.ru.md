# Объявление ресурсов — `defineAbilities`

**[English](define-abilities.md) · [Русский](define-abilities.ru.md)**

Всё, что библиотека знает о ваших ресурсах, берётся из одной схемы: какие есть ресурсы, что с ними можно делать и как они связаны. Отсюда же выводятся и все типы — имена ресурсов, доступные каждому действия, форма строки. Ни одного объединения или кортежа писать руками не придётся.

```ts
import { defineAbilities, shape } from "@vetojs/core";

const ac = defineAbilities({
	resources: {
		post: {
			schema: shape<Post>(),
			actions: ["read", "create", "update", "delete", "publish"],
			relations: {
				blog: { resource: "blog", kind: "one" },
				comments: { resource: "comment", kind: "many" },
			},
		},
		blog: { schema: shape<Blog>(), actions: ["read", "update"] },
		comment: { schema: shape<Comment>(), actions: ["read", "create", "delete"] },
	},
});
```

Во время работы функция просто возвращает `resources` без изменений — по сути это типизированная тождественная функция. Вся польза в типе, который она запоминает.

## Из чего состоит ресурс

| Поле | Что означает |
|---|---|
| `schema` | собственные поля строки; необязательное — у ресурса без строк его не пишут ([см. ниже](#ресурс-без-строк)). `shape<T>()` — метка, которая ничего не делает во время работы и только несёт тип; передайте настоящую [Standard Schema](https://standardschema.dev), если хотите ещё и проверять данные — [см. ниже](#подставить-настоящую-схему-вместо-typet) |
| `actions` | что можно делать с этим ресурсом; запоминается как литералы |
| `relations` | именованные связи с другими ресурсами — `{ resource, kind }`, где `kind` это `"one"` или `"many"` |

**Имена** связей выбираете вы, а **цель** обязана быть объявленным ресурсом. Имена связей живут отдельно от полей схемы — ровно так же ваш ORM разделяет колонки и `include`/`with`.

## Ресурс без строк

Экран, отчёт, фоновая задача — то, о чём политика принимает решение, но за чем нигде не стоит запись. Не пишите `schema`.

```ts
const ac = defineAbilities({
	resources: {
		post: { schema: shape<Post>(), actions: ["read", "update"] },
		report: { actions: ["view", "export"] },
	},
});
```

Всё остальное как обычно: у `report` свои действия, правила пишутся так же, а `can("view", "report")` отвечает по этим правилам.

Меняется форма — теперь она пустая, и в этом весь смысл. Строку по ошибке не передашь, и ни одно условие не сравнит поле, которого у ресурса никогда не было:

```ts
const ac = defineAbilities({ resources: { report: { actions: ["view"] } } });
const { allow } = createRules(ac);
const ability = buildAbility(ac, []);

ability.can("view", "report", { id: "r1" });        // ✗ у ресурса без строк нет строки, которую можно передать
allow("view", "report", { where: { id: "r1" } });   // ✗ и нет поля, по которому пишут условие
```

`ability.validate("report", data)` по-прежнему отвечает: принимает любой объект и отвергает всё остальное — ровно как `shape<T>()` без валидатора. Необъявленный ресурс так и остаётся неизвестным, так что «объявлен, но пустой» и «не ресурс» — разные ответы.

[Адаптеру Drizzle](./drizzle.ru.md#ресурсы-без-таблицы) об этом сообщают отдельно: `defineTables(ac, { report: null })`. Объявление говорит, что у ресурса нет формы; карта — что у него нет таблицы.

Если же экран чем-то **определяется** — идентификатором воркспейса из маршрута, — то строка у него всё-таки есть, и это тот самый ключ. Тогда его объявляют: [гейтинг экрана](./react.ru.md#экраны-и-вкладки--ресурсы-без-строк) как раз про этот случай.

## Подставить настоящую схему вместо `shape<T>()`

`shape<T>()` стирается при сборке: она заносит форму в систему типов и во время работы не проверяет ничего. Передайте вместо неё [Standard Schema](https://standardschema.dev) — и то же самое объявление начнёт ещё и проверять входящие данные:

```ts
import { z } from "zod";

const post = z.object({
	id: z.string(),
	authorId: z.string(),
	status: z.enum(["draft", "published"]),
	views: z.number(),
});

const ac = defineAbilities({
	resources: { post: { schema: post, actions: ["read", "update"] } },
});
```

`ShapeOf<AC, "post">` теперь выводится из схемы, то есть ничего не описывается дважды, а `ability.validate` начинает делать настоящую работу:

```ts
ability.validate("post", { id: "p1", authorId: "u1", status: "published", views: 10 });
// → { ok: true, value: … }

ability.validate("post", { id: 1, status: "archived" });
// → { ok: false, issues: […] }
```

Это вторая половина работы с недоверенным вводом, и половины отвечают на разные вопросы:

| | Вопрос |
|---|---|
| `validate` | а это вообще корректный пост? |
| `validatePayload` | можно ли этому пользователю писать эти поля и значения? — см. [запись](./mutations.ru.md) |

Типичная ошибка — вызвать только одно из двух. Данные бывают безупречны по форме и при этом трогают поле, которое пользователю писать нельзя; бывает и наоборот — политика разрешает, а содержимое бессмысленно.

> **Схема должна проверять синхронно.** Сверено со Standard Schema v1: **Zod, Valibot и ArkType** работают. **Yup — нет**: стандарт он реализует, но проверка у него асинхронная, и `validate` бросит исключение, а не вернёт промис, который легко забыть дождаться.

Больше не меняется ничего. Правила, вычисление и `can()` к схеме не обращаются: движок читает поля структурно и тотален на любом вводе, поэтому схема добавляет проверку только на границе.

## Что получается на выходе

```ts
type AC = typeof ac;

ResourceName<AC>;      // "post" | "blog" | "comment"
ActionFor<AC, "post">;      // "read" | "create" | "update" | "delete" | "publish" | "manage" — что называет правило
DeclaredAction<AC, "post">; // "read" | "create" | "update" | "delete" | "publish" — что называет вопрос
ShapeOf<AC, "post">;   // Post
```

Дальше эти типы уходят в `createRules(ac)` и `buildAbility(ac, …)`. Поэтому опечатка в названии действия или поля оборачивается ошибкой компиляции, а не правилом, которое молча никогда не сработает.

## Почему так устроено

- **Параметр типа `const` вместо `as const`.** Литеральные названия действий запоминаются сами собой, и объявление остаётся чистым.
- **У каждого ресурса своя форма.** Общий параметр формы слепил бы разные ресурсы в один, а `ShapeOf` читает каждую `schema` по отдельности.
- **`schema` несёт тип, а не данные.** `shape<T>()` нужна лишь затем, чтобы протащить `T` в систему типов, и во время работы не стоит ничего. Подставьте Standard Schema, когда понадобится, чтобы `ability.validate` действительно проверял входящие данные — см. [ability](./ability.ru.md).
- **Правило, ссылающееся на необъявленное, не пройдёт.** У типизированных фабрик это ошибка компиляции; для правил, приходящих в виде JSON, та же проверка выполняется на границе доверия — см. [parse](./parse.ru.md).
